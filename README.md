# Home Solar dashboard (MomHome · MhuHome)

One dashboard for several homes' solar systems. Switch between them with the ▾ next to the
name in the header.

| Home | System | Data | Bills |
|---|---|---|---|
| **MomHome** | 7.44 kWp, Solis S6-EH1P10K-L-PLUS, 16 kWh LiFePO4, zero export | SolisCloud exports: 5-min + monthly (daily rows) | PEA Log |
| **MhuHome** | 5 kWp Huawei, no battery, installed 20/09/2020 | FusionSolar monthly reports, from 23/09/2020 (via `solar_pipeline`) | MEA Log |

Each home only gets the pages its data supports. MomHome has all six. MhuHome has Overview,
Trends and Savings; Day and Health need 5-minute data, and Battery needs a battery.
Product brief and KPI formulas: `MomHome/design_handoff_momhome_solar/project.md`.

Laid out like findash: a Python package under `src/` (pipelines + FastAPI data API) and a
TypeScript frontend under `frontend/`, with typed `lib/api.ts` + TanStack Query hooks.

## Your data vs the sample data

Real data is **never committed**. `frontend/public/data/` (the processed CSVs and
`homes.json`), `raw_samples/` and `.env` are git-ignored. The repo ships
**`sample_data/`** instead: invented days for both homes in the same layout, generated by
`scripts/make_sample_data.py`. Only the tariffs and `ft_rates.csv` are real, and both are
public. On a fresh clone, `npm run dev` / `npm run build` copy `sample_data/` into
`frontend/public/data/` if it has no `homes.json`. `scripts/refresh_all.sh` then replaces it
with your own data. The API tests run on `sample_data/`.

Local settings go in `.env` (copy `.env.example`): the raw-export folders, the bills
spreadsheet and the data folder.

## Open it

If you run a local Caddy proxy with the `solar.localhost` sites, then
**<http://solar.localhost:8080>** is always on with nothing to start. It serves the production
build and reads `frontend/public/data` live, so:

- new data: `scripts/refresh_all.sh`, then refresh the browser;
- code changes: `cd frontend && npm run build` (or use <http://solar-dev.localhost:8080> with
  `npm run dev` for live reload);
- optional API: <http://solar-api.localhost:8080> with `.venv/bin/uvicorn momsolar.api.app:app --port 8020`.

Bookmarks: `#/momhome/`, `#/mhuhome/`, `#/mhuhome/savings`, `#/momhome/day`, …

## Run

```bash
# Frontend (static files, no server needed)
cd frontend && npm install
npm run dev            # http://localhost:5173  → #/momhome/ , #/mhuhome/trends , …
npm test               # vitest
npm run build          # → frontend/dist, a static site that runs from any folder

# Python (pipelines + API)
python3.12 -m venv .venv && .venv/bin/pip install -e ".[api,dev]"
.venv/bin/pytest
.venv/bin/uvicorn momsolar.api.app:app --reload --port 8020   # http://127.0.0.1:8020/docs
# then: VITE_API_BASE_URL=http://solar-api.localhost:8080 npm run dev
```

## Update the data

```bash
cp .env.example .env    # once: set MOMSOLAR_SOLIS_RAW_DIR / MOMSOLAR_HUAWEI_RAW_DIR (and MOMSOLAR_SHEET)
scripts/refresh_all.sh                                       # inverter data for both homes
MOMSOLAR_SHEET=~/Downloads/PEA.xlsx scripts/refresh_all.sh   # + PEA/MEA bills and Ft (Google Sheet → File → Download → .xlsx)
```

It runs these, which you can also run on their own:

```bash
.venv/bin/python -m momsolar.fetch_solis_day --home momhome --raw "<Solar Energy>/MomHome" [--pea-log PEA.xlsx]
.venv/bin/python -m momsolar.fetch_huawei    --home mhuhome --raw "<Solar Energy>/Raw from Inverter report" [--mea-log PEA.xlsx]
```

- **SolisCloud API (MomHome):** with `MOMSOLAR_SOLIS_KEY_ID` / `MOMSOLAR_SOLIS_KEY_SECRET`
  in `.env` (SolisCloud → Account → Basic Settings → API Management), `refresh_all.sh` and
  `POST /refresh` also pull the last two days: 5-min readings (`inverterDay`) and that month's
  daily rows (`inverterMonth`), merged exactly like the exports. Backfill with
  `.venv/bin/python -m momsolar.fetch_solis_api --since 2026-03-29`; inspect raw replies with
  `python -m momsolar.solis_api probe` (saved to git-ignored `raw_api/`). Checked against the
  exports: every daily field and all 5-min power/SOC/counter fields match. The API has no alarm
  code or per-port load counters, so those are blank; the day's load total is Solis's own.
- **Files are recognised by their header row, not their name.** SolisCloud reuses
  "Inverter History Report_…" for different exports, and FusionSolar has used three names for
  the same report. Anything else in the folders (plant reports, a Power BI export) is skipped.
- **MomHome:** the monthly inverter report gives `daily.csv`. The 5-min All-History export
  gives `5min.csv`; a newer export of a day replaces the whole day. The early (Mar/Apr 2026)
  54-column 5-min layout is skipped, because it has no grid power.
- **MhuHome:** `solar_pipeline` (a separate Gmail fetcher) saves each month's
  FusionSolar report from Gmail into `Raw from Inverter report/Y<year>/` on the 1st.
  `fetch_huawei` reads that folder recursively, so run `scripts/refresh_all.sh` after it
  (or chain it — see below).
- **Bills:** the sheet is private, so download it as .xlsx. The PEA Log's Year / Usage Month
  are broken formulas, so the usage month comes from `Month Year`. The MEA Log's are valid and
  used as-is (its bill is dated the following month), and the amount is its
  `ค่าไฟฟ้ารวม VAT` column. Bills are matched to solar data by **usage month** for both homes.
- Rows merge by key (day, 5-min time, usage month), so re-running is always safe.

To refresh right after the Gmail fetch, add one line to the end of
`solar_pipeline/run.sh`, or to the launchd job: `<this repo>/scripts/refresh_all.sh`.

## How savings are estimated

Without-solar bill = Type 1.2 tiers on (inverter load − inverter import + billed units) +
service + Ft × units, × 1.07 VAT. Saved = that − the actual bill. Per home (`homes.json`):

- **Tariff:** PEA's service charge is ฿38.22 and MEA's ฿24.62. Both use the same tiers
  (3.2484 / 4.2218 / 4.4217).
- **TOU bills** (MEA from 03/2025, on/off-peak units logged): the actual bill plus the solar
  used at home, priced at the on-peak rate (5.7982) on weekdays and off-peak (2.6369) at
  weekends, plus Ft and VAT. Daily data can't split the hours, so all weekday solar counts as
  on-peak, a slight overestimate.
- **TOU meter analysis** (Savings, homes with TOU bills; `lib/tou.ts`): each TOU bill vs the
  normal tiers on the same units ((normal − TOU energy) × VAT; service and Ft cancel), the
  on-peak share vs its **break-even** share (above it the normal tariff would be cheaper), and
  the on-peak share estimated without solar. Bills whose on + off-peak units don't add up to
  the billed units (MEA Log Oct and Nov 2025 repeat Sep's split) are flagged and left out.
- **`meterNetsExport`** (MhuHome: true): until 2024 the MEA meter netted exports. Billed
  units track Huawei import − export to within tens of kWh, while import alone is 150–470 kWh
  higher. So each exported kWh cancelled an imported one at the retail rate, and the estimate
  adds export back. Since 2025 export is 0, so this doesn't affect later months. Set it to
  false to count export as worth nothing.
- **`exportRate`**: a separate buy-back payment per exported kWh (0 for both homes).
- **Ft** comes from the sheet's Ft history (2019 →). A month missing from it falls back to an
  Ft back-solved from the pre-solar bill.

## Missing data is never drawn as zero

- A day with no PV value isn't loaded (MhuHome: 115 days, including Nov 2025 – mid-Feb 2026).
  Its month is hatched.
- A day with PV but no usable meter values keeps its PV; its load, import and export count as
  missing. That covers days with no meter readings (8 days of Sep 2021), days with load but a
  blank grid import (22 days of May and all of Jun–Aug 2021), and a no-battery day showing 0
  import, since such a home always draws from the grid at night. The Overview cards and the
  Sankey use the same days, so they always agree; Trends' "Solar produced" counts every day.
- A bill whose usage month has no meter data is shown as "no solar data" and left out of the
  savings, not counted as ฿0 saved.
- **Known outages** go in `homes.json` → `dataGaps` (`from`, `to`, `reason`, `reasonTh`). They're
  shown by name instead of "not loaded": MhuHome's inverter lost its cloud connection
  31/10/2025 – 15/02/2026 (per the FusionSolar reports). A period with no data at all shows a
  hatched "No data" panel and "—" cards on the Overview, never 0 %.
- **Estimates for missing inverter data** (`lib/estimate.ts`; homes without a battery; on by
  default, switch off in Settings). Every day after switch-on with missing PV or meter values
  is filled and marked **est.**: dashed bars (PV dashed only where PV itself was estimated),
  "d est." under months, est. tags on days and bills, and an "Estimated" CSV column.
  - PV: measured where it exists; otherwise the same month's daily average a year earlier
    (else another year). If the home was on zero export, that month's export isn't copied.
  - Grid import: **from the bill**, i.e. billed units minus the real days' import, spread over
    the missing days (netting meter: export added back, so Σ(import − export) = billed units).
    The meter gap for those months is therefore ~0 by construction.
  - Load = PV − export + import. MhuHome: 237 days (Feb 2024, May 2021 – Sep 2021 meter,
    May 2025, the Oct 2025 – Feb 2026 outage, May 2026). The raw CSVs are never changed.
- 5-min gaps show hatched in the SOC heatmap and the completeness grid. KPI tests use
  `design/data/day.json` and project.md §2 (`src/lib/__fixtures__/`).

## Notes

- **Units:** energy shows in kWh below 1,000 and in MWh from 1,000 (4,032 kWh → 4.03 MWh).
  Bills, per-day figures and charts stay in kWh.
- **Hover explanations:** every card and every Sankey node explains what it means and how it's
  worked out (tap on a phone). "Losses & inverter use" is the balance: inverter conversion,
  the inverter's own running power and report rounding, plus battery round-trip loss.

- **System cost (capex) for payback** is `systemCost` in `homes.json`, per home.
  `systemCostPlaceholder: true` shows the "placeholder" tag. A viewer can override it in **Settings** (gear icon), along with the
  effective ฿/kWh rate and show-losses; those overrides are saved per browser.
- **Grid → battery** is taken as 0 (Solis doesn't split charging by source) and is drawn as the
  dashed zero link.
- **Switch-on date** is `installed` in `homes.json` (MomHome 29/03/2026, MhuHome 20/09/2020). It
  starts every "since switch-on" range, the payback projection and the before-solar baseline.
  Days between it and the first report (MhuHome 20–22/09/2020) are missing days, estimated like
  any other; the switch-on month's bill isn't used for their import, as it also covers pre-solar days.
- **Old links** without a home (`#/day`) open the first home in `homes.json`.
- No auth on the API. Keep it LAN/VPN-only.
